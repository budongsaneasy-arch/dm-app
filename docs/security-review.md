# DM 템플릿 연동 보안 점검

- 점검일: 2026-10-26
- 대상: `dm-app` @ `8067fdd` (https://dmapp.bdseasy.com)
- 사양: [docs/querystring-prefill.md](./querystring-prefill.md)

본 서비스(bdseasy.com)에서 DM 생성기로 중개사무소 정보를 넘기는 쿼리스트링 방식을 점검했습니다.
**앱 코드에서는 문제를 찾지 못했고, 문제는 전달 방식 하나에 있습니다.**

조치가 필요한 항목 **1건**, 안전하게 구현된 항목 **9건**.

---

## 1. 조치 필요 — 쿼리스트링은 제3자 서버에 전달됩니다

DM 생성기는 URL의 값을 **브라우저에서만** 읽어 입력 폼을 채웁니다. 서버로 보내는 코드는 없습니다.
그런데 `?` 로 시작하는 쿼리스트링은 **HTTP 요청라인의 일부**라서, 브라우저가 페이지를 받아오는
그 첫 요청에 이미 포함되어 전송됩니다.

```
GET /?bizName=…&regNo=…&repName=…&phone1=…&phone2=010-0000-0000&address=… HTTP/1.1
Host: dmapp.bdseasy.com
```

dmapp은 GitHub Pages로 호스팅되고 그 앞단은 Fastly CDN입니다. 응답 헤더에서 확인했습니다.

```
Server: GitHub.com
Via: 1.1 varnish
X-Fastly-Request-ID: …
X-GitHub-Request-Id: …
```

요청마다 식별자가 붙으므로 **두 곳의 접근 로그에 URL 전체가 남을 수 있습니다.** 로그 보관 정책은 통제할 수 없습니다.

한 가지는 분명히 해 둡니다. **응답 본문에는 개인정보가 전혀 들어가지 않습니다.** dmapp이 내려주는 HTML은
누구에게나 동일한 1,104 바이트 정적 파일이고, CDN 캐시를 통해 다른 사람에게 새어 나갈 경로는 없습니다.
노출되는 것은 **요청 URL 그 자체**입니다.

### 해결: `?` 를 `#` 으로

프래그먼트(`#` 뒤)는 브라우저가 서버로 보내지 않습니다. 실제로 확인했습니다.

| 방식 | 보낸 주소 | 서버가 보는 것 |
| --- | --- | --- |
| `?` 쿼리스트링 (현재) | `…/?phone2=010-0000-0000` | `GET /?phone2=010-0000-0000` |
| `#` 프래그먼트 (권고) | `…/#phone2=010-0000-0000` | `GET /` |

양쪽 앱을 모두 고쳐야 하는 변경입니다.

- **보내는 쪽**: `?` 대신 `#` 으로 조립
- **받는 쪽**: `queryPrefill.js` 에서 `location.search` → `location.hash.slice(1)` (한 줄)

값 자르기·공백 제거·허용 목록·적용 후 주소창 정리 로직은 그대로 두면 됩니다.

## 2. 전달되는 6개 항목의 민감도

6개 중 5개는 중개사무소 등록 정보로, 중개대상물 광고에 의무 표기하는 공개 정보입니다.
성격이 다른 것은 `phone2` 하나입니다.

| 파라미터 | 내용 | 성격 |
| --- | --- | --- |
| `phone2` | 대표 개인 휴대전화 | **개인정보** |
| `bizName` | 상호 | 공개 정보 |
| `regNo` | 개설등록번호 | 공개 정보 |
| `repName` | 대표명 | 공개 정보 |
| `phone1` | 사무소 전화 | 공개 정보 |
| `address` | 사무소 주소 | 공개 정보 |

개인정보를 외부 사업자(GitHub·Fastly) 인프라로 전송하는 것이 처리위탁에 해당하는지는 법률 검토가
필요한 영역입니다. `#` 방식으로 바꾸면 이 쟁점 자체가 사라집니다.

## 3. 점검 결과 문제가 없던 항목

| 항목 | 확인 내용 |
| --- | --- |
| XSS | `v-html` 두 곳이 있으나 모두 `<` `>` `&` 를 이스케이프한 뒤 고정 마크업만 넣고, 출력 위치가 속성이 아닌 요소 내용이라 안전합니다. 해당 두 필드(`addrNote`, `closing`)는 URL로 주입할 수 없습니다. |
| 파라미터 주입 | 허용 목록 6개만 읽고 나머지는 무시합니다. `bizType`·`greetBody` 등을 URL로 넣어도 모델이 바뀌지 않는 것을 테스트로 확인했습니다. |
| 입력값 처리 | 외부 입력으로 취급해 `trim()` 후 항목별 글자수 제한(20·22·10·20·20·44)으로 자릅니다. |
| 코드 실행 | `eval`, `new Function` 사용 없음. |
| 데이터 유출 경로 | 앱 코드에 외부 전송(`fetch`·XHR·`sendBeacon`·WebSocket)이 전혀 없습니다. 외부 호스트는 Google Fonts 둘뿐입니다. |
| Referer 유출 | Google Fonts 요청에는 브라우저 기본 정책(`strict-origin-when-cross-origin`)에 따라 출처만 전달되고 쿼리는 포함되지 않습니다. |
| 주소창 잔류 | 적용 후 `history.replaceState` 로 쿼리를 지웁니다. 새로고침해도 사용자가 고친 값이 URL 값으로 되돌아가지 않는 것을 확인했습니다. |
| 전송 구간 | HTTPS 강제. `http` → `https` 301 리다이렉트, 인증서 검증 정상. |
| 저장소 노출 | 공개 저장소이지만 샘플 데이터가 전부 가상값이고, 실제 사무소 정보·고객 데이터는 커밋되지 않습니다. |

## 4. 함께 짚어 둘 사항

### 공용 PC의 localStorage 잔류 — 검토 권고

입력값은 `dm_model` 키로 브라우저에 자동 저장됩니다. 사무소 정보 6개뿐 아니라 중개사가 DM에 입력한
**단지명·시세·사례까지 전부** 포함되며, 기간 제한 없이 남습니다. 사무실 공용 PC에서 쓰면 다음 사용자가
그대로 볼 수 있습니다. (출처가 분리돼 있어 다른 사이트가 읽을 수는 없습니다.)

**"입력 정보 지우기" 버튼**을 두는 것을 권합니다.

### 보안 응답 헤더 없음 — 검토 권고

`Content-Security-Policy`, `X-Frame-Options`, `Referrer-Policy`, `Strict-Transport-Security`,
`X-Content-Type-Options` 모두 없습니다. GitHub Pages는 정적 호스팅이라 응답 헤더를 설정할 수 없습니다.

`<meta>` 태그로 CSP와 Referrer-Policy는 보완할 수 있지만, **iframe 삽입 차단(`frame-ancestors`)은
meta 로는 적용되지 않습니다.** 정적 호스팅의 구조적 한계이며, 헤더 제어가 필요하면 호스팅을 옮겨야 합니다.

### 본 서비스 라우트 작업 시 참고

- 이동 목적지는 **코드에 고정**하세요. URL 파라미터로 받으면 오픈 리다이렉트가 됩니다.
- `target="_blank"` 링크에 `rel="noopener"` 를 붙이세요. 최신 브라우저는 기본 적용하지만 명시하는 편이 안전합니다.
- 계정 정보 조회가 비동기이므로 `await` 뒤에 `window.open` 을 부르면 팝업 차단에 걸립니다.
- 허용 목록에 `addrNote`·`closing` 은 **절대 추가하지 마세요.** 이 두 필드만 `v-html` 로 출력됩니다.

## 5. 권고 — 우선순위 순

1. **`?` 쿼리스트링을 `#` 프래그먼트로 변경** — 개인정보가 제3자 서버에 전달되는 경로를 원천 차단합니다. 양쪽 앱 모두 수정이 필요하며, 받는 쪽은 한 줄입니다. 사양서 합의가 먼저입니다.
2. **`phone2` 전달이 꼭 필요한지 재검토** — 빼면 넘기는 값이 전부 공개 정보가 됩니다. 한 번 입력하면 브라우저에 저장되니, 중개사가 직접 입력하게 두는 선택지도 있습니다.
3. **"입력 정보 지우기" 버튼 추가** — 공용 PC 대응. 사무소 정보 6개만 `sessionStorage` 로 옮기는 방법도 있습니다.
4. **`meta` 태그로 CSP·Referrer-Policy 명시** — 지금도 브라우저 기본값으로 막히지만, 명시하면 구형 브라우저까지 보장됩니다. 심층 방어 수준의 조치입니다.

## 6. 이 점검이 다루지 않은 것

- **본 서비스(bdseasy.com) 쪽 코드는 점검 대상이 아니었습니다.** 계정 정보를 꺼내는 `member/info` API의 권한 검사나 세션 처리는 보지 않았습니다.
- **로그인 세션이 필요한 실제 연동 흐름은 확인하지 못했습니다.** 실제 사무소 정보가 채워져 넘어가는지는 개발팀이 확인해야 합니다.
- **GitHub·Fastly의 로그 보관 정책은 확인할 수 없습니다.** 로그가 남는다는 전제로 판단했습니다.
- 의존성 취약점 점검(`npm audit`)은 범위에 넣지 않았습니다. 설치 시점 기준 보고된 취약점은 0건이었습니다.
